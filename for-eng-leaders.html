    3C — for engineering leaders¶

    3C — Claude Code Coach — is built by one architect with a public steward. That's not a confession; it's how we keep retros tight and decisions auditable.

    This is the page to forward when you're making the case for a rollout to a CTO or a board. It answers the four questions that usually come up: what it costs, what it buys, what happens if the architect steps away, and how you reverse it.

    What L1 costs you¶

    • Adoption time: one week — a focused adoption sprint — from npx 3c init to the whole team's assistants sharing a spine. The standards / workflow / quality baseline is captured on day 1 and the delta measured by end of week, so the rollout proves itself inside the sprint rather than on faith.
    • Infrastructure: none — L1 runs on developer workstations. No backend, no service to operate, no data-processing agreement.
    • Vendor lock-in: none. The workflow skills conform to the Agent Skills open standard and the licence is MIT — fork it, keep it, replace it.
    • Ongoing maintenance: a steward role of ~2 hr/week per active 6–15-developer team — curating rules from retrospectives, not babysitting infrastructure.

    What L1 buys you¶

    Anchored to the three pillars — and these are the measured end-of-adoption-week deltas the sprint captures (convention-consistency on AI-authored diffs; the share of changes moving through the /3c-* skills; the pre-commit gate pass-rate and what it caught pre-review), not promises that mature on faith. They are visible by the end of the adoption week and compound from there:

    • Standards layer → by the end of the adoption week, two engineers on the same repo produce structurally consistent code without a reviewer forcing it. Architectural drift stops compounding.
    • Workflow layer → by the end of the adoption week, issue-creation, implementation, review, and test-generation run the same way on every laptop — onboarding a new hire is reading one CLAUDE.md, not shadowing for a month.
    • Quality layer → by the end of the adoption week, lint/types/tests/secret-scan run before code review, every commit — the review queue stops absorbing what a gate should have caught.

    What L2 adds — shipped May 2026 (v1.5.0)¶

    L2 is the Automate level. Same install, same .claude/ footprint, same reversal posture — but the standards your team agreed to at L1 now enforce themselves before code review.

    For the eng-leader audience, the things to forward up:

    • The gate chain becomes automatic. Post-Edit Validation runs at the point of AI generation (<300ms); the Coverage Gate and Security Scan Gate run pre-PR; the Standards Drift Detector runs on demand. Every gate is independently disable-able and writes a JSONL event regardless of pass / fail / bypass. The review queue stops absorbing what a gate should have caught — and you can prove it from the events log without asking developers.
    • Coaching mode turns gate failures into mentorship moments. When a junior's commit fails the hook, the failure message includes the rule's rationale, an example of the right shape, and a link to the ADR or incident that produced it. The thing senior engineers normally do in PR review, automated. Off-switch in .3c/coaching.yaml. The Standards Rationale Database (/3c-explain <rule-id>) is the structured backbone — every rule traceable to its origin.
    • The PM-tool integration is no longer GitHub-only. /3c-create-issue now routes to Jira Cloud, Linear, GitLab Issues, and GitHub via the bundled MCP server. Tokens via OS keychain only — never cached, never returned in tool output, never committable. Same skill UX across all four.
    • White-label deployment is one command. npx 3c init --brand="<Brand Name>" plus npx 3c skills install copies your team's skills and agents in under their own slash prefix (e.g. /acme-*, with specialists acme-architect / acme-code-reviewer) against the upstream kgn-git/3C source — no fork, the files live in your repo under git. The deployment-init CLI is the path from "we adopted 3C" to "we have our AI coding standards" without forking a maintained dependency.
    • Your senior-review process, made consistent. The L2 surface grew a multi-agent crew that runs the review-and-delivery process your best engineers run by hand — the same way on every change, regardless of who is at the keyboard or what hour it is. /3c-review-board convenes eight specialist reviewers (architecture, code, security, tests, product, UX, QA, customer-journey) and reconciles their findings into one deterministic verdict — blocking, advisory, or clean — with genuine disagreements surfaced for a human rather than averaged away. /3c-project-manager carries an issue through that review on the way to a PR; /3c-programme-manager does it for a dependency-ordered chain of projects across one workspace. Every verdict is advisory and every git action is checkpointed — the crew accelerates the process, it does not take the decision. It is also the bridge to L3: these per-change verdicts are exactly what the L3 dashboards roll up.

    What L2 does NOT change:

    • No backend, no telemetry egress. L2 events are local JSONL on the developer workstation. There is still no 3C-hosted service, no opt-in tier, no telemetry pipe to a vendor. L3 introduces a self-hostable backend; L2 does not.
    • No new vendor lock-in. Still MIT, still Agent Skills standard, still git-installable, still git revert-removable.
    • No compliance or regulatory framing. That business case is parked. L2 is a developer-productivity and team-quality layer, full stop.

    The L2 adoption sprint is the same shape as L1: one focused week from npm install ...#v1.5.0 to measurable deltas. The four metrics it captures: pre-PR gate pass-rate, post-edit validation findings per AI-authored diff, coaching-mode rationale link-throughs, and drift-detector audit delta week-over-week. If you're at L1 and your team is ready for the next level, the L2 today page is the technical brief; this page is the business one.

    Bus-factor and succession¶

    Here's how succession works in this project — the steward role is documented and transferable; fork rights are explicit (MIT); contributor pathway is open via GitHub Discussions; any structural change to project governance will be announced in an ADR before code lands. We do not yet have a named succession plan; we have a succession process.

    The architect¶

    3C is maintained by one architect with a public steward, working in the open at github.com/kgn-git — public role, public commit history, public contributor pathway via GitHub Discussions. The full public bio (name, role, contact) is steward-reviewed and confirmed by the architect before public launch, per this page's non-negotiable verification gate — it is not auto-generated. What is verifiable today is the work itself: every decision is an ADR, every sprint a handover, every change a reviewed PR.

    L3 backend commercial intent¶

    L3 introduces a self-hostable backend dependency. No commercial entity, hosted offering, or paid tier is planned at this time. If that changes, it will be announced in an ADR before any code lands.

    Reversal in one PR¶

    L1 is reversible. To remove 3C entirely: git revert the PR that added .claude/ (or git rm -r .claude/ && git commit). What remains afterward: nothing of 3C's — the .claude/ tree is the entire footprint. No daemon to uninstall, no global package, no workstation state, no backend to decommission. The codebase is exactly what it was, minus the conventions you chose to keep.
