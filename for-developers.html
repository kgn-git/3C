    3C — for developers¶

    This page is for the IC sitting in front of Claude Code today. Not your manager, not your CISO — you, the person who will actually use this thing every commit.

    We'll be honest about what changes for you and what doesn't. 3C is built on the principle that the worst thing a governance framework can do is slow you down. So everything below is designed around two questions: what new thing do I have to think about? and what gets faster?

    What changes on day one¶

    After npx 3c init, npx 3c skills install, and npx 3c hook install (run npx 3c doctor to confirm they landed), three things are different in your daily flow:

    1. Your AI assistant has read the team's conventions. npx 3c init writes a CLAUDE.md into the repo root with your team's standards distilled into a single file under 150 instructions. The AI will spontaneously follow them. You will stop reviewing PRs where the AI used a pattern your team retired six months ago.
    2. A pre-commit hook runs before every commit. npx 3c hook install registers it: lint, types, unit tests, secret scan — under a 10-second budget on a typical repo. Catches the obvious before your reviewer has to.
    3. Four slash commands appear in Claude Code. npx 3c skills install copies them in: /3c-create-issue, /3c-implement, /3c-review, /3c-test. Each runs the standardised version of those workflows for your team. You can ignore them — the L1 standards still apply through CLAUDE.md — but they're the fastest path through the same lifecycle that everyone on your team is now running.

    That's L1. It's enough for a long time.

    What L2 adds for you specifically¶

    L2 — v1.5, shipped May 2026 — is where 3C starts paying you back for the conventions L1 captured. Five things start mattering for the IC:

    Pre-commit gates that catch the obvious before review¶

    Beyond L1's lint / types / unit-tests / secret-scan baseline, L2 adds three more gates that fire automatically before code review:

    • Post-Edit Validation runs the moment Claude Code finishes an edit — checks imports, naming, and architectural-direction rules against the change. Catches "the AI imported from internal/" or "the AI named it getUser when our convention is fetchUser" in <300ms, before you've even staged the file.
    • Coverage Gate refuses to PR a change that drops coverage below the team threshold. Tunable per test type (unit / integration / contract). Off by default; turn it on when the team's actually ready for it.
    • Security Scan Gate runs SAST + dependency-vulnerability scan per commit. Refuses on critical findings; warns on lower severities. You get the warning in the same buffer as the test failures — no separate dashboard to check.

    All gates write a JSONL event regardless of pass / fail / bypass, so the picture stays complete even when you /3c-bypass --reason="hotfix" to ship a critical change.

    Coaching mode — the hook tells you why, not just no¶

    The annoying part of pre-commit hooks is they fail you at the worst time and tell you nothing. L2 changes that.

    When a rule fails and coaching mode is on, the hook output includes:

    • The rule's rationale (why it exists).
    • A 5-line example of the right shape.
    • A link to the ADR or incident that produced the rule, if one exists.

    It's the thing senior engineers do in code review, automated and immediate. Turn it off in .3c/coaching.yaml once the team's past needing it — the rules still enforce, you just stop seeing the explanations.

    Activation: coaching is ON by default — you don't need to do anything to enable it. To disable for the whole repo, write enabled: false into .3c/coaching.yaml. To disable for specific users only, use disabledUsers: [<user>] in the same file.

    The rationale itself comes from the Standards Rationale Database: a structured "why" repository linking every rule to its origin. You can also look it up directly with /3c-explain <rule-id> when you're curious why a rule exists without waiting for it to bite you.

    → Coaching mode in full covers the rationale-authoring path, the adaptive teaching after two sightings, and what coaching deliberately does NOT do.

    Your AI assistant gets two more agents¶

    L1 shipped code-reviewer and test-author as subagents your AI can dispatch. L2 adds two more:

    • architect — for "I'm about to make a design decision and want a second opinion that knows our ADRs and patterns."
    • security-reviewer — for "I'm touching auth / crypto / input-handling and want the OWASP + CWE lens applied before I PR this."

    Both are plain Markdown files under .claude/agents/ with declared tool allowlists — you can read them, fork them, change them. No black box.

    The crew — multi-lens review and orchestrated delivery, on demand¶

    Those agents started as something your AI dispatches one at a time. The L2 surface then grew the roster to eight (adding product-owner, ux-expert, qa-reviewer, journey-architect) and wired them into a crew you drive with three explicit commands — they only run when you type them:

    • /3c-review-board — run the whole panel over your branch before you open the PR. The eight specialists each report findings; the board reconciles them into one verdict — blocking, advisory, or clean — de-duplicating what they agree on and flagging where two disagree on severity for you to settle. The reconciliation is tested code (3c reconcile), so the same diff gives the same verdict every time — not a model mood.
    • /3c-project-manager — hand it an issue and it drives the whole pipeline: enrich → plan → test-first → review board → PR. It checkpoints before it branches or opens a PR, and it never merges, force-pushes, or bypasses a hook on your behalf. You stay in control of anything irreversible.
    • /3c-programme-manager — when your work spans several projects in one workspace (a monorepo, or sibling folders), it sequences them in dependency order with a checkpoint between each, reading the ledger at .3c/dependencies.yaml.

    The verdict is always advisory — you decide. Run npx 3c doctor if you ever wonder whether the crew installed cleanly; it checks all eight agents and three orchestrators are wired.

    Cross-platform workflow skills¶

    If your team uses Jira Cloud, Linear, or GitLab Issues instead of GitHub: /3c-create-issue now routes to all four. Token via OS keychain (Keychain on macOS, Credential Manager on Windows, Secret Service on Linux). Nothing cached, nothing returned in tool output, nothing committable as a secret.

    If your test runner is Mocha, Playwright, or JUnit (not just Jest / Vitest / Pytest): /3c-test recognises and scaffolds for those too. New at L2: an integration-test mode separate from unit-test scaffolding.

    Your own local insights dashboard¶

    L2 captures hook telemetry to .3c/events/*.jsonl — local-only, gitignored, never egressed at L2. The Personal Local Insights Dashboard renders it as a static HTML file you open in your browser:

    • Which rules fire most for you (so you know what to internalise).
    • How often your commits pass the gate on first try (so you know if coaching mode is still earning its keep).
    • The post-edit validation deltas trend (so you can see your own AI-assisted-quality curve).

    It's the developer's mirror of what the L3 team-backend dashboard will roll up across the team — but at L2, the data does not leave your machine. Your manager can't see this dashboard. Only you can.

    What L2 does NOT change for you¶

    The framework is designed to disappear when it's not needed. So:

    • You can still bypass. /3c-bypass --reason="hotfix for prod" skips the hook chain for the next commit. Logged in the JSONL events; never silently suppressed.
    • You can still edit by hand. The post-edit validator only fires when Claude Code is the editor. Editing a file directly in your IDE bypasses it — same as if the file didn't have rules. (This is intentional; 3C governs AI-assisted change, not human IDE work.)
    • Your model interactions don't change. Whether Claude Code is talking to Sonnet, Opus, or a local model — 3C sits between you and the editor, not between Claude Code and its provider. Your existing model-traffic agreement is undisturbed.
    • You don't have to learn a new tool. The four L1 slash commands plus the L2 additions (/3c-drift, /3c-standards history, /3c-explain, /3c-deploy, /3c-bug, /3c-onboard, /3c-bypass) and the crew orchestrators (/3c-review-board, /3c-project-manager, /3c-programme-manager) all live where every other Claude Code skill does. There's no separate CLI to keep open in another terminal.

    How to adopt L2 if you're already at L1¶

    Realistically, half a day of focused work for the IC who's championing it:

    1. npm install git+https://github.com/kgn-git/3C#v1.7.3 — pin v1.7.
    2. npx 3c setup — one command provisions everything (CLAUDE.md, rules, hooks, the L2 skills, the crew agents product-owner/ux-expert/qa-reviewer, an inert arch-check), then runs 3c doctor to verify. Idempotent over an existing L1 tree, which it preserves; the individual init / skills install / agents install / hook install commands still run on their own if you prefer to step through.
    3. npx 3c doctor — re-check anytime; it now also flags a stale 3c CLI that's behind your installed skills, so a degraded crew skill tells you to upgrade instead of failing quietly.
    4. Enable one gate at a time and watch the JSONL events accumulate for a few days before turning on the next. Recommended sequence: Post-Edit Validation → Coaching Mode → Drift Detector → Coverage Gate → Security Scan Gate.
    5. Open .3c/dashboard.html after a week and see your own data.
    6. After shipping a piece of work, optionally capture a retrospective with /3c-retrospective <scope> — a single-project, evidence-based retro that is a suggestion, never a gate.

    What we're learning

    The patterns that work best are coaching mode + drift detector together — coaching catches the per-commit issues with rationale, drift catches the slow regressions that landed before a rule was written. If you're trying this on your own team, tell us how it goes.
