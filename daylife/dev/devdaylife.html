    Prompt: "A day in the life of a developer using 3C" — infographic¶

    Source material on disk: site/index.html, site/why-now.html, site/maturity-model.html, site/l1-today.html, site/l2-today.html, site/for-developers.html, site/coaching.html, site/branding.html, site/infographic/sdlc-infographic.html (the visual template), site/infographic/diagrams/*.mmd (existing mermaid sources), site/diagrams/{day-with-3c,journey,pillars}.svg.

    Goal¶

    Produce a multi-page, print-ready HTML infographic titled "A day in the life of a developer using 3C." It tells the working day of one engineer (call her Maya) who is shipping inside a team that has adopted 3C — Claude Code Coach at L2 (v1.5.0, May 2026), and it makes the workflow legible at a glance: one phase per page, one diagram per phase, one key message per phase.

    The deliverable is a standalone .html file that mirrors the structure, design system, and print posture of site/infographic/sdlc-infographic.html — same A4 portrait pages, same typography, same colour tokens, same badge / title / diagram / key- message / footer rhythm — so the new infographic sits next to the existing one as a sibling deliverable, not a one-off.

    Audience¶

    A new engineer joining a team that already runs 3C at L2. Assumes general familiarity with Git, sprint-based agile workflows, TDD, and PR review, plus everyday use of Claude Code as her AI assistant — but zero prior knowledge of 3C itself, its slash commands, its rule files, its subagents, or its gate chain.

    Hard constraints — Maya never edits code or tests by hand¶

    This is non-negotiable, and the writer must read this section before starting the diagrams.

    Maya is an instructor, not a typist. Every code change, every test change, every fix, every refactor in this infographic happens through Claude Code (her AI assistant) or through one of the /3c-* slash commands — never by Maya opening a file in her IDE and editing it manually. This is true even for:

    • writing the assertions in a TDD test (she prompts /3c-test or Claude Code with the assertions she wants in natural language; the skill or the assistant types them)
    • fixing a failing test (she re-prompts Claude Code with the diagnosis, or dispatches the architect / code-reviewer subagent for a second opinion, and lets the assistant apply the fix)
    • tightening an issue body that came back too vague (she iterates with /3c-create-issue until it is right)
    • correcting a coaching-mode rule violation (she re-prompts Claude Code with the rationale she just read in the coaching segment)

    Maya does type freely in three places, and only these three:

    1. Prompts — to Claude Code, to the slash commands, to subagents.
    2. Issue / PR comments in GitHub.
    3. Config-style decisions — picking the next issue, choosing a branch name, approving a destructive-operation prompt with y, running /3c-bypass --reason="..." for a real hot-fix.

    If a phase seems to demand hand-editing, that is a signal the phase is under-specified — re-prompt or re-dispatch instead. The infographic should reinforce this discipline visibly: in every diagram, the arrow that changes code is labelled with the slash command or the assistant that did the typing.

    What to establish on the cover page¶

    Before the seven phase pages, a cover page establishes:

    • The premise. 3C is AI engineering alignment: keeping every team member's AI assistant working from the same conventions, the same workflow, and the same quality bar. Without it, every session is locally optimal but the aggregate is locally optimal, globally incoherent (site/why-now.html).
    • The three pillars — Standards (CLAUDE.md under a hard 150-instruction cognitive budget, .claude/rules/, the architecture pattern library, the security policy templates), Workflow (the slash commands), Quality (the gate chain). site/diagrams/pillars.svg may be inlined or recreated as a small inset.
    • The L2 surface area Maya uses today — slash commands /3c-create-issue, /3c-implement, /3c-review, /3c-test, /3c-drift, /3c-standards history, /3c-explain <rule-id>, /3c-deploy, /3c-bug, /3c-onboard, /3c-onboard-guide, /3c-bypass; the crew orchestrators /3c-review-board, /3c-project-manager, /3c-programme-manager; the eight review agents architect, code-reviewer, security-reviewer, test-author, product-owner, ux-expert, qa-reviewer, journey-architect; gate chain Post-Edit Validation (< 300 ms) → Pre-Commit (< 10 s) → Coverage Gate + Security Scan Gate (< 60 s) → Drift Detector (on-demand).
    • Coaching mode — ON by default; teaching segment shape (——— 3c coaching ——— block) shown verbatim in a sidebar so the reader recognises it later; goes terse after TERSE_AFTER = 2 sightings of the same rule by the same developer.
    • The brand caveat (one line, drawn from site/branding.html) — if this team has run npx 3c init --brand="Acme" and chosen the slug acme, the reader will see /acme-review in their terminal instead of /3c-review; the slash prefix is brand-controlled, the upstream code is not. The infographic uses the unbranded /3c-* names throughout for clarity.
    • The honesty discipline — 3C deliberately under-claims; reversal is git revert of one PR; no source code leaves the workstation.

    Design system — copy from sdlc-infographic.html¶

    The visual brief is exactly the existing infographic's stylesheet — do not invent a new design language. The writer should re-use:

    • A4 portrait pages, 210 × 297 mm, with padding: 14mm 14mm, page-break-after: always; cover and closing get padding: 18mm 16mm.
    • Fonts: Inter (300/400/500/600/700/800/900) for everything, JetBrains Mono for tags, badges, page numbers, and prompt/event snippets. Both from fonts.googleapis.com.
    • Colour tokens — re-use the existing CSS custom properties exactly: --indigo-{50,100,500,600,700,900}, --slate-{50,100,200,500,700,900}, --amber-{100,600}, --emerald-{50,500,700}. Indigo for orchestration and skills; amber for shared-context / rationales / coaching; emerald for quality gates passing; red (#FEE2E2 / #DC2626 / #7F1D1D) for failure / refusal states.
    • Per-page chrome: a .page-header with a left-side .badge (mono-font, 01 · INTAKE style) and a right-side .page-num (1 / 7); an H2 .diagram-title (~26pt, weight 800, letter-spacing -0.02em); a .diagram-subtitle (~12pt); the .diagram-wrap (use .tall for sequence diagrams, .xl for the Phase 5 state machine); a .key-message indigo-tinted box at the bottom (.key-label mono uppercase + .key-text 13.5pt weight 500); a .page-footer with the phase name on the left and a rule / artefact reference on the right.
    • Cover page: gradient background, eyebrow, large .cover-title (~48pt with one <span> accent), .cover-sub, three .hl highlight cards in a 3-col grid, .cover-meta strip with version and 3C — Claude Code Coach brand block.
    • Closing page: gradient background, .closing-head eyebrow, .closing-title (~40pt), .closing-body (~14pt), a 2-col .takeaway-grid of six .takeaway cards (numbered), and a .closing-cta strip with the GitHub source and the topic tags.

    The writer should literally open site/infographic/sdlc-infographic.html, copy its <style> block wholesale, and adapt only what the new content requires (e.g. adding a small "coaching segment" callout style and a prompt/snippet style).

    Diagram requirements — one per phase¶

    All diagrams are mermaid sources. The writer should commit a .mmd file per diagram into site/infographic/diagrams/ following the existing naming pattern (f-intake.mmd, g-enrichment.mmd, h-batch.mmd, i-sprint-assembly.mmd, j-implement.mmd, k-sprint-throughput.mmd, l-uat.mmd, m-dashboard.mmd), pre-render each to SVG with the same toolchain (puppeteer.config.json is already in the folder), and inline the SVGs into the HTML at the <!--SVG_F--> style placeholders.

    Every mermaid source must begin with the same %%{init: ...}%% theme block the existing five diagrams use, so the typography and palette match. Pick the right diagram type per phase:

    Diagram F — Phase 1 — Intake → issue creation (flowchart TD)¶

    Nodes: PM Brief, Slack Thread, CSV (customer feedback) → /3c-create-issue prompt → iteration loop → GitHub Issue (structured: title, user-story, scope, out-of-scope, ACs, deps, source- link). Label the iteration arrow Maya re-prompts /3c-create-issue explicitly. Annotate the GitHub Issue node with the 6 required fields as a sub-list. Footer reference: L2 Multi-PM MCP adapter · GitHub default at L1.

    Diagram G — Phase 2 — Technical enrichment (sequenceDiagram)¶

    Actors: Maya, architect (subagent), /3c-explain (skill), GitHub Issue. Steps: Maya dispatches architect with the issue context; architect returns affected components / approach / risks / open questions / complexity / testing strategy; Maya reads, identifies one proposed pattern that doesn't fit the codebase, runs /3c-explain <rule-id> against a rule she's not sure about, pushes back to architect with the rationale, gets a revised analysis, appends it to the GitHub Issue. Critical: no node labelled "Maya edits the analysis" — every change to the analysis is made by architect after Maya's prompt or by /3c-implement later.

    Diagram H — Phase 3 — Batch backlog refinement (flowchart LR)¶

    Funnel: 18 raw items → batch prompt template → /3c-create-issue ×18 → near-duplicate detection (a diamond decision node; merged duplicates loop back into the count) → human-clarification flag (a small branch off for items that are internally contradictory or missing context — these do not proceed) → /3c-drift check that no issue references a non-existent rule → cleaned set (e.g. 12 ready, 4 merged, 2 flagged for human clarification). The diagram makes the funnel shape visible: 18 in, 12 out, with the lost mass labelled.

    Diagram I — Phase 4 — Sprint assembly (flowchart TB)¶

    A 5-check grid above a single output node. Top row, left to right: overlap scan, AC contradiction scan, missing-deps scan, coverage-gap scan, doc-uniformity scan — each invoked by /3c-review adapted for sprint scope, with /3c-standards history as a side-node feeding all five. Bottom node: Tightened sprint (deduplicated, internally consistent) with one issue explicitly punted (a side-arrow labelled needs ADR-level discussion).

    Diagram J — Phase 5 — One issue, end-to-end (stateDiagram-v2)¶

    The most detailed diagram — give it the .xl diagram-wrap class. States, in order: Issue selected → /3c-implement plan → branch created → /3c-test scaffolds failing tests → Claude Code implements → Post-Edit Validator (<300ms) → loop back to Claude Code on failure → git stage + commit → Pre-Commit Hook (<10s) (lint / types / unit / secret) → loop back on failure with coaching segment shown → Coverage Gate + Security Scan Gate (<60s) → /3c-implement PR description → /3c-review-board → eight-agent panel (architect, code-reviewer, security-reviewer, test-author, product-owner, ux-expert, qa-reviewer, journey-architect) → reconciled verdict (blocking / advisory / clean) → Maya prompts Claude Code to apply the applicable findings → merge to main. Show the verdict as advisory — Maya still decides. Every edge that changes code is labelled with who typed it (Claude Code applies, /3c-implement applies, /3c-test scaffolds) — never Maya.

    Diagram K — Phase 6 — Working the rest of the sprint (flowchart TD)¶

    A compounding loop: Issue 2 → Issue 3 → Issue 4, each running through a compact box labelled /3c-implement (full loop, see Diagram J). Off to the side, three loops that get tighter each iteration: - Coaching loop: verbose teaching segment on issue 2 → terse on issue 4 (annotate TERSE_AFTER = 2). - Pattern-reuse loop: prompt to /3c-implement references the merged PR ("follow the shape of #1284") — no re-pasting of standards into context (annotate 150-instruction budget held). - Subagent loop: architect dispatched once for a hard design call; security-reviewer dispatched before PR for an auth-touching change.

    A side-branch shows the hot-fix path: prod incident → /3c-bypass --reason="prod hotfix #INC-417" → JSONL event recorded → ship → follow-up issue auto-created.

    A second side-branch shows the tricky-failure path (this is the one to design carefully so it stays consistent with the hard constraint above): Pre-Commit fails on tricky test → Maya reads coaching rationale → Maya prompts Claude Code: "the rule is right, the test asserts the wrong contract, regenerate it" → Claude Code revises the test → gate passes. No node labelled "Maya edits the test in IDE" — instead, the diagram makes visible that the rule's authority routes the fix through the assistant, not around it.

    Diagram L — Phase 7 — Manual end-user testing (sequenceDiagram)¶

    Actors: Maya, /3c-test --mode=integration, /3c-deploy, Staging environment, /3c-bug, GitHub Issue. Sequence: Maya invokes /3c-test --mode=integration for a UI/integration change → skill scaffolds a UAT checklist + edge cases (test-author subagent assists) → Maya invokes /3c-deploy --env=staging → deploy runs pre-flight checks → health check passes → Maya runs the checklist manually in staging → finds a regression → Maya invokes /3c-bug → skill captures OS, runtime, project state, recent commits, scrubbed env vars → structured report appended to original GitHub Issue → Maya comments and reopens or marks done. Annotate the production-deploy arrow with requires --yes.

    Diagram M — End-of-day reflection (pie or flowchart)¶

    A small mock-up of the Personal Local Insights Dashboard at .3c/dashboard.html. Three panels: - Rules that fired most for me today (top 5 list) - First-try gate pass-rate (one big number, e.g. "78%") - Post-edit validation deltas trend (sparkline placeholder)

    Annotate plainly: local-only · gitignored · never egressed at L2 · your manager cannot see this.

    Phase narratives — body copy under each diagram¶

    The diagram carries the structure; the body copy (placed inside the .diagram-subtitle slot and, for richer phases, an additional small prose block above the .key-message) carries Maya's voice. Each phase narrative should:

    • Open with one sentence on what Maya is doing and why.
    • Show one concrete artifact verbatim in a .snippet block:
    • Phase 1 — the literal /3c-create-issue prompt she sends, then the resulting issue body (truncated to ~10 lines).
    • Phase 2 — the architect subagent's output snippet (3–4 bullet points), then a one-line /3c-explain <rule-id> invocation and its reply.
    • Phase 3 — the batch-prompt template (5 lines) and the human- clarification flag email/comment (2 lines).
    • Phase 4 — the /3c-review adapted prompt and its summary of findings (5 lines).

    • Phase 5 — the coaching teaching segment exactly as shipped:

      ——— 3c coaching ———
• import-order
Why:  imports should be ordered stdlib, third-party, local —
      fewer merge conflicts in long-lived branches.
Do:   import { readFile } from "node:fs/promises";
Docs: https://kgn-git.github.io/3C/
———————————————

      plus a JSONL gate event verbatim (one line). - Phase 6 — a terse coaching segment (bullet + Why: only) and the JSONL bypass event with the reason field populated. - Phase 7 — a /3c-bug structured report header (5 lines, scrubbed). - Close with the three call-outs (as compact bullets, not boxes — the .key-message box already does the visual emphasis): - What 3C does for you here. - What Maya still owns here. (always a thinking / judgement action, never a typing action) - What 3C deliberately does NOT do here.

    Cap each phase body copy at ~180 words so the page stays scannable and the diagram dominates.

    Closing page (page 9) — common mistakes + checklist¶

    Two stacked sections inside the existing .closing layout:

    Common mistakes — six cards (re-use the .takeaway-grid / .takeaway styles, but number them with a red .takeaway-num accent instead of indigo, and rename the class for the rendered file). Each card is one sentence on the mistake plus one sentence on the correction. Required mistakes:

    1. Rubber-stamping AI-generated issues; correction: read every issue body before publishing — /3c-create-issue produces what you prompt, not what you mean.
    2. Pasting the entire standards doc into prompts; correction: trust the .claude/rules/ library and the 150-instruction budget — re- pasting blows the budget and degrades the model.
    3. Bypassing without a real --reason; correction: the JSONL event is permanent and reviewable — "forgot why" in the reason field is how teams lose trust in the bypass mechanism.
    4. Treating coaching segments as noise; correction: the second sighting goes terse on its own — read it the first time and the framework gets quieter on its own.
    5. Running /3c-implement on issues that haven't been enriched; correction: enrich first (Phase 2), then implement — architect is cheaper before code than after.
    6. Trying to edit code or tests by hand to "save time"; correction: the assistant types, you instruct — every hand-edit is a missed opportunity for the rule library to evolve.

    Pinnable checklist (single card spanning both columns, ≤ 20 lines). Required content, in this order:

    • Slash commands by phase: /3c-create-issue · /3c-explain · /3c-drift · /3c-review · /3c-standards history · /3c-implement · /3c-test [--mode=integration] · /3c-deploy --env=<…> · /3c-bug · /3c-bypass --reason="...".
    • Subagents and when to dispatch each: architect (design call), security-reviewer (auth/crypto/input-handling), code-reviewer (pre-PR findings), test-author (test scaffolding inside /3c-test), product-owner (scope/priority), ux-expert (screen-level UX), qa-reviewer (AC traceability), journey-architect (journey reachability) — or convene all eight at once with /3c-review-board, which reconciles their findings into one verdict.
    • Gate chain in firing order: Post-Edit Validation (< 300 ms) → Pre-Commit (< 10 s) → Coverage + Security Scan (< 60 s) → Drift (on-demand).
    • Bypass syntax: /3c-bypass --reason="<one-line>" — logged, never silent.
    • File paths to remember: CLAUDE.md (root, ≤ 150 instructions), .claude/rules/<rule>.rationale.yaml, .3c/coaching.yaml, .3c/coaching/<user>.yaml, .3c/events/*.jsonl, .3c/dashboard.html.
    • The one rule that summarises the rest: the assistant types, you instruct.

    Tone¶

    • Match the 3C house voice — calm, honest, mildly understated, names what it does NOT do at every step. Read site/why-now.html and site/for-developers.html and lift the cadence directly.
    • Match the existing infographic's punchy diagram titles ("Skills talk to skills — on purpose."). Each of the seven phase titles should read as a single, opinionated sentence with a full stop. Examples the writer can refine but should not copy verbatim:
    • Phase 1: "Raw inputs in. Reviewable issue out."
    • Phase 5: "One issue, six gates, zero hand-edits."
    • Phase 6: "Compounding is the product."
    • No emoji except the small lifecycle emoji already used in the source .mmd files (🔧 🏁 📚 🔄). Do not introduce new emoji.
