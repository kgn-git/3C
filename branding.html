    3C — deploying with custom branding¶

    3C can deploy under your team's own brand without forking the source — same upstream code, your slash-command prefix, your name on the experience. This page covers what ${BRAND_*} means, how the brand slug propagates through a copy install, and what stays upstream when your team adopts the framework.

    If you just want to use the framework as-is, you don't need to do anything here — the defaults work, and every command reads /3c-<skill>. Read this only when you want /acme-review instead of /3c-review for your team.

    The two-tier identity model¶

    3C adopts a two-tier brand identity (the architecture decision is AD-16 in strategy/adr/). One tier is immutable upstream; the other is per-deployment.

    • ${FRAMEWORK_*} — the upstream framework identity. Set in framework.json at the source repo. Immutable for adopters: FRAMEWORK_NAME = 3C, FRAMEWORK_SLUG = 3c, FRAMEWORK_LONG = Claude Code Coach, FRAMEWORK_VERSION = 1.7.3. These govern marketing, ADRs, the canonical kgn-git/praise repo, and the upstream community.
    • ${BRAND_*} — your team's per-deployment identity. Chosen at init time and persisted in your project's branding.json. Governs the slash-command prefix on the skills and agents copied into your repo, the OS-keychain prefix, the .<slug>/ runtime paths, and the contents of internal docs the framework generates into your project.

    When you do nothing, ${BRAND_*} falls through to ${FRAMEWORK_*} — the framework runs unbranded as 3c. When you set a brand, only the per-deployment tier changes; the upstream tier stays.

    What each token namespaces¶

    Token What it controls Default value (when no branding.json) After choosing the slug acme
    BRAND_NAME Human-readable name in docs, CLI banners, errors 3C Acme
    BRAND_SLUG Slash-command prefix on copied skills + agents (/<slug>-<verb>), .<slug>/ runtime paths, OS-keychain prefix 3c acme
    BRAND_LONG Long-form display name (e.g. in PDF exports, landing copy) Claude Code Coach Acme Coding Standards
    BRAND_VERSION Your deployment's version (independent of upstream framework version) 1.7.3 0.1.0
    FRAMEWORK_SLUG Upstream CLI binary name (npx <slug> ...) — unchanged by branding 3c (immutable) 3c (still — adopters invoke via the upstream npm package)
    FRAMEWORK_VERSION Pinned upstream version recorded in praise.config.json UPSTREAM_REF 1.7.3 (immutable) 1.7.3 (the version your team pinned at init)

    In template files, tokens are wrapped with the dollar-brace syntax (${ ... }) and substituted at install time with the values from framework.json + branding.json. The table above lists the token names without that wrapper for readability; in template sources you write the wrapper around each name.

    With the slug acme, your team types /acme-review to invoke the review skill, and the review board's specialists install as acme-architect, acme-code-reviewer, and so on — but the skill code and CLI itself still come from the upstream 3c package on npm install. The brand changes only the deployment-facing surface.

    How to deploy under your own brand¶

    White-label runs through the default copy install — the same path every team uses, with the brand slug set once. There is no separate branded build to maintain.

    # 1. Pin the upstream framework (v1.5.0 = L2; v1.0.0 = L1-only)
npm install git+https://github.com/kgn-git/3C#v1.7.3

# 2. Scaffold, choosing your namespace at the prompt
npx 3c init --brand="Acme"
#   → "Keep the 3c namespace? [Y/n]" → n → enter a brand slug → acme

# 3. Copy the skills and agents in under your slug
npx 3c skills install
npx 3c agents install

# 4. Confirm the wiring is coherent end-to-end
npx 3c doctor

    The brand slug propagates deterministically through the install:

    Surface What the slug does Result with acme
    branding.json Holds the four BRAND_* values The source of truth for every substitution below
    Skills (.claude/skills/) Each skill folder + name: is prefixed with the slug at copy time /acme-create-issue, /acme-review, /acme-project-manager, …
    Agents (.claude/agents/) Each agent filename + name: is prefixed with the slug acme-architect, acme-code-reviewer, acme-test-author, …
    Runtime paths The .<slug>/ config + telemetry directory .acme/events/, .acme/dependencies.yaml, .acme/coaching.yaml
    praise.config.json Records the upstream pin + brand summary FRAMEWORK_VERSION, BRAND_SLUG, UPSTREAM_REF, INSTALL_UUID

    init validates your BRAND_SLUG against a reserved-name blocklist (anthropic-*, claude-*, agent-skills, claude, claude-code) and a kebab-case pattern (a-z0-9-, 3–32 chars). Invalid input gives an actionable error before any file is written. Choose a single clean token (acme, not acme-standards) so the hyphen reads cleanly as the namespace separator in /acme-<skill>.

    npx 3c doctor then verifies the result is coherent: every skill and agent prefixed with your slug, no stale /3c-* cross-references left behind, both hooks registered, and no unsubstituted ${BRAND_*} tokens. It is the fastest way to confirm a rebrand took cleanly.

    Why copy install is the default¶

    The copy path puts the skills, agents, and rules in your repo, under git. That is deliberate: your team evolves those files from retrospectives — tightening a review checklist, adding a rule, refining the project-manager pipeline — and the changes travel with the repo like any other code. Upstream improvements arrive via npm install of a newer pin, applied with npx 3c init against your existing tree.

    Optional: the plugin / marketplace path¶

    A Claude Code plugin install is also shipped, for teams that prefer the marketplace distribution model. It uses .claude-plugin/plugin.json (name: 3c) and yields the colon namespace /<slug>:<verb> instead of the hyphen form. The trade-off: a plugin install is cached outside your repo, so retrospective edits to skills need a commit → /plugin marketplace update → /reload-plugins cycle rather than a plain git pull. Most teams should use the copy default; the plugin path remains available if your distribution constraints call for it.

    What stays framework-level¶

    Per AD-16, certain things never get per-brand overrides:

    • MIT license — 3C is MIT-licensed; your deployment inherits MIT. Fork rights are explicit; no per-deployment EULA.
    • Upstream provenance — every deployment's praise.config.json records UPSTREAM_REF (the git tag you pinned, e.g. v1.5.0) and INSTALL_UUID. The 3c verify-commit command runs against the upstream tag during init — refuses to scaffold from an unsigned upstream (supply-chain provenance, not an audit chain).
    • The canonical source repo — kgn-git/praise. PRs / issues / discussions live upstream; your deployment's branding.json is your own, but bug reports and feature requests funnel back to one place.
    • The 3c npm bin name — npx 3c always invokes the upstream CLI; your 3c namespaces the artefacts the CLI produces, not the CLI itself.

    What custom branding does NOT enable¶

    The same honesty discipline as the rest of this site:

    • No compliance attribution. The two-tier model exists for white-label adoption, not for compliance signaling. Regulatory framing (ISO 42001 / EU AI Act / AIMS) was extracted from the L1–L4 model per epic #166; your brand does not confer compliance status from upstream. Compliance content is parked in strategy/parked/compliance-business-case.md.
    • No white-label SaaS. 3C is open-source software, not a vendor product. Custom branding lets your team's tooling carry your team's name; it does not create a commercial product or a service-level agreement.
    • No upstream-attribution stripping. Even with brand set, praise.config.json records the upstream pin and the framework name. Your team gets to brand the experience; the supply chain stays auditable.

    Brand immutability after init¶

    Brand is set at init time and persists in branding.json. There is no 3c rebrand command. To change brand, edit branding.json directly and re-run npx 3c init followed by npx 3c skills install / npx 3c agents install — that re-derives the slug and re-copies the artefacts under the new prefix. Run npx 3c doctor afterwards to confirm no stale references remain.

    For most teams, brand is a one-time decision at deployment. We chose immutability over a rebrand workflow because (a) slash prefixes are referenced from every developer's local Claude Code state, and unilateral rename would break in-flight sessions; (b) the upstream INSTALL_UUID makes per-brand-per-install state inspectable for support cases. If your team genuinely needs a rebrand workflow, start a discussion.

    • The full init --brand CLI spec ships in issue #60; the verification-via-signed-tag path is AC5 on that issue.
    • The brand-substrate code (slug validation, blocklist, branding.json schema) shipped in issue #57 — it's the shared module reused by the deployer.

    What we're learning

    Teams that adopted 3C under their own brand report that the white-label adoption helped buy-in — "our team's AI coding standards" reads differently to engineers than "an external framework's defaults". The flip side: keep INSTALL_UUID somewhere your support process can find it, because debugging across multiple branded deployments is hard without it. If you are working through a brand decision, start a discussion.
