    Skills vs Agents¶

    3C ships two kinds of extension that are easy to confuse. They are invoked in completely different ways.

    The one-line model¶

    • Skills are user-invoked slash commands — you type them (/3c-review).
    • Agents (subagents) are dispatched workers — a skill, or Claude itself, hands a bounded task to one via the Task tool. You never type an agent as a slash command.
    Skill Agent
    Lives in .claude/skills/<name>/SKILL.md .claude/agents/<name>.md
    Invoked by you, as /3c-<name> a skill / Claude, via the Task tool
    Selected how you choose it (or, if model-invocable, Claude may auto-run it) by matching the agent's description, or named by a skill
    Runs in the main conversation a fresh, isolated context window
    List them 3c skills list 3c agents list

    Why agents aren't slash commands¶

    An agent is a specialist persona (e.g. a read-only reviewer) that runs in its own context so it can do focused, bounded work — a long diff scan, a security pass — without crowding the main thread. Because they're a delegation mechanism, not a command mechanism, they have no slash form. To use one explicitly, ask in plain language ("use the code-reviewer subagent on this diff"), or run the skill it's paired with.

    Worked example: /3c-review → 3c-code-reviewer¶

    1. You run the skill: /3c-review.
    2. The skill dispatches the 3c-code-reviewer subagent (read-only: Read, Grep, Glob) for the long-context diff scan, in a fresh context.
    3. The subagent returns structured findings; the skill formats and prints them.

    You typed one thing (/3c-review); the agent ran underneath it. The shipped agents — 3c-architect, 3c-code-reviewer, 3c-security-reviewer, 3c-test-author — are each paired to a skill this way.

    Namespace¶

    Commands install under a hyphen brand prefix: /3c-<skill> by default, or /<brand>-<skill> if you set a custom namespace at 3c init. Run 3c skills list to see exactly what's installed and how each is invoked.

    Orchestration convention (composing the crew)¶

    Some skills are orchestrators: they convene several specialist agents and combine their output. Because a subagent can never spawn another subagent, the orchestration always lives in a skill (the main thread), not in agent-to-agent calls. The convention any orchestrator follows:

    1. Dispatch one level deep, in parallel. The skill issues one Task call per specialist agent in a single turn, each in a fresh context. No agent dispatches another agent.
    2. Collect findings in the shared schema. Each agent returns a fenced json array of { severity, category, message, file?, line?, suggestion? }.
    3. Reconcile deterministically. The skill assembles { "<agent>": [findings] } and pipes it to 3c reconcile, which de-dupes, merges cross-agent agreement, ranks, flags conflicts, and returns one verdict. Reconciliation is tested code, not prose, so the verdict is reproducible.
    4. Stay read-only / local unless the skill explicitly owns a checkpointed write step.

    /3c-review-board is the worked example: it dispatches 3c-code-reviewer, 3c-architect, 3c-security-reviewer, 3c-qa-reviewer (and 3c-ux-expert for UI changes) in parallel, then reconciles. Teams can compose their own boards or pipelines from the installed agent roster by following these four steps.
