A day in the life of
a developer using 3C.

One engineer's working day inside a team that has adopted 3C — Claude Code Coach at L2 (v1.5.0). The slash commands she runs, the gates she passes, the rules that coach her, and the things she never types by hand.

Standards
CLAUDE.md under a 150-instruction cognitive budget, .claude/rules/, the architecture pattern library, the security policy templates — the shared spine every AI session reads from.
Workflow
The /3c-* slash commands — create-issue, implement, review, test, drift, explain, deploy, bug, onboard, bypass. The same lifecycle on every laptop.
Quality
Post-Edit Validation (<300ms) → Pre-Commit Hook (<10s) → Coverage Gate + Security Scan Gate (<60s) → Drift Detector on demand. Every gate fired, every event logged.

Specialists on call: the AI dispatches code-reviewer, test-author, architect, and security-reviewer when one perspective isn't enough. Coaching mode: gate failures explain why, not just no — rationale, example, ADR link — and go terse after two sightings of the same rule. Honesty discipline: one git revert removes 3C entirely; no source code leaves the workstation; the framework under-claims by design.

One brand note: if Maya's team ran npx 3c init --brand="Acme Standards", she invokes /acme-standards:review instead of /3c-review. This infographic uses the unbranded /3c-* names throughout for clarity. The upstream code is unchanged; only the slash namespace is brand-local.

01 · INTAKE
1 / 7

Raw inputs in. Reviewable issue out.

Maya's morning starts with a PM brief, a Slack thread, and a CSV of customer feedback. She invokes /3c-create-issue, iterates on the draft, and ends with one GitHub issue carrying six required fields. The assistant types the issue body; Maya picks intent and judges fit.

The exact prompt Maya sends, and the resulting issue body she reviews:

/3c-create-issue --repo=acme/web We want logged-in users to see their last 5 orders on the account home. PM brief attached (link). Source: customer feedback CSV row 247, Slack #cx-feedback 2026-05-19. Out of scope: changing order-detail page.
Title: account home: surface last 5 orders User story: As a logged-in user, I want my last 5 orders… Scope: account-home page, /api/orders pagination Out of scope: order-detail page, reordering, returns AC1: orders panel shows 5 most-recent orders, descending by date AC2: empty state when user has zero orders AC3: link to full order history (existing route) Deps: none new. Source: Slack #cx-feedback…

What 3C does for you here: turns three loose inputs into one structured artefact in under a minute. What Maya still owns: reading the draft and judging "is this what I meant?" — the only typing she does is the next prompt. What 3C does NOT do: read source files, scrape Slack, or transmit anything to GitHub except the title / body / labels / repo Maya explicitly provided.

Key takeaway
The skill produces what you prompt, not what you mean. Iterating the prompt is the work; reading the draft is the gate.
Phase 1 · Intake

02 · ENRICH
2 / 7

Dispatch a specialist before code.

The issue is structured, not yet technical. Maya dispatches the architect subagent for an approach analysis, looks up the rationale for a pattern she's unsure about with /3c-explain, and re-prompts the architect with the rationale until the analysis fits.

What the architect returns (first pass), and Maya's /3c-explain lookup:

Affected: src/account/home/, src/api/orders/list.ts Approach: paginate via existing /api/orders?limit=5&sort=-date Risks: stale-cache on order-creation (TTL 5 min on this route) Open questions: empty state copy? confirm with PM Complexity: S (≤ 1 day) Testing: unit on pagination + integration on empty state
/3c-explain layered-mvc.api-vs-page-boundary Why: API routes own data shape; page components consume + render. A page importing another page's data layer is a boundary violation. Do: fetch in the page route handler, hand props to component Docs: kgn-git.github.io/3C/

What 3C does for you: dispatches a specialist that reads your standards before answering. What Maya still owns: noticing the analysis doesn't fit, and choosing to re-dispatch — the architect re-writes; Maya doesn't. What 3C does NOT do: design the solution unilaterally; the architect proposes, you accept or push back.

Key takeaway
The architect is cheaper before code than after. One re-dispatch with a rationale beats fifty minutes of refactoring.
Phase 2 · Enrichment
L2 architect + security-reviewer subagents (VP-02-F11b)
03 · BATCH
3 / 7

Eighteen rows in. Twelve issues out.

After lunch, Maya processes the backlog dump. A batch prompt template runs /3c-create-issue against each row; duplicates collapse, two items kick back for human clarification, and /3c-drift catches any reference to a rule that has since been retired.

The batch template Maya wraps each row in, and the clarification comment she sends back to the PM for one of the rejected items:

/3c-create-issue --batch --repo=acme/web For each row in customer-feedback.csv: - title from "summary" column - user-story from "asker_voice" column - source-link from row URL - mark as "needs human clarification" if "type" column is empty
Hi Sam — row 12 of cx-feedback says "shipping flow broken on mobile" but no device / steps / expected behaviour. Two issues about shipping in the same week, possibly the same bug. Could you (or a customer) attach a screen recording and confirm? — Maya (via /3c-bug template)

What 3C does for you: consistent shape across eighteen issues + dedup + drift check, in one pass. What Maya still owns: reading the two flagged items and deciding "ask the human" vs "drop it". What 3C does NOT do: invent acceptance criteria for unclear rows; the human-clarification branch is the framework saying "I cannot make this concrete; you decide."

Key takeaway
The funnel shape is the point: 18 in, 12 out, 4 merged, 2 deferred. The framework loses items on purpose, not by accident.

04 · ASSEMBLE
4 / 7

Five scans, one tightened sprint.

With 12 clean issues in hand, Maya runs /3c-review over the sprint as a whole — five checks that catch the inconsistencies a single-issue review misses. /3c-standards history feeds every check so the assertions match the rules that existed on the relevant date.

The /3c-review invocation adapted for sprint scope, and the resulting summary of findings:

/3c-review --scope=sprint --issues=#1284..#1295 For the 12 issues in the candidate sprint: 1. flag overlapping files across issues 2. flag contradictory ACs across issues 3. flag deps that aren't in scope 4. flag modules changed without test issues 5. flag issue-body shape uniformity
Findings: - #1287 + #1291 both touch src/account/home/. Merge order matters. - #1289 AC2 contradicts #1284 AC3 on empty-state. Decide. - #1292 depends on a util that #1295 will refactor. Sequence. - #1290 changes /api/orders/ but no test-issue. PUNT to needs-ADR. - 11/12 issue bodies match shape. #1293 missing out-of-scope.

What 3C does for you: five inconsistency checks across the whole sprint, dated against the rules that actually applied. What Maya still owns: choosing whether to merge, sequence, or punt each finding — the skill flags, she decides. What 3C does NOT do: reject the sprint; one issue gets punted for ADR-level discussion, the rest proceed.

Key takeaway
Catching a contradiction now costs five minutes. Catching it in PR review costs two days of rework.

05 · IMPLEMENT
5 / 7

One issue, six gates, zero hand-edits.

Maya picks issue #1284 and runs /3c-implement. From branch creation through merge, every keystroke that changes code, tests, or the PR description is typed by Claude Code or by a /3c-* skill. Maya prompts, judges, and approves.

The coaching segment Maya sees when the Pre-Commit hook flags her import order, and the JSONL event the hook telemetry records:

——— 3c coaching ——— • import-order Why: imports should be ordered stdlib, third-party, local — fewer merge conflicts in long-lived branches. Do: import { readFile } from "node:fs/promises"; Docs: kgn-git.github.io/3C/ ———————————————
{"ts":"2026-05-20T14:32:11Z","gate":"pre-commit","rule":"import-order","outcome":"fail","duration_ms":487,"file":"src/account/home/orders-panel.tsx","user":"maya","session":"j-1284-2"}

What 3C does for you: six gates fire automatically; failures explain why; every event is recorded. What Maya still owns: reading the coaching segment, deciding "rule is right, regenerate" vs "rule is wrong, push to standards-history". What 3C does NOT do: fix the code for her unbidden — every revision happens because Maya re-prompted Claude Code with the diagnosis.

Key takeaway
The gate chain is mechanical. The instruction is human. The keystroke is always the assistant's.
Phase 5 · Implementation loop
L2 Post-Edit (#16) · Coverage (#17) · Security Scan (#18) · Coaching (#23)
06 · COMPOUND
6 / 7

Compounding is the product.

After issue #1284 ships, Maya runs issues #1285, #1286, #1287 through the same loop. Coaching goes terse on rules she has seen twice. New prompts reference shipped PRs as patterns, holding the 150-instruction budget. The hot-fix path and the tricky-failure path both route through the assistant — never around it.

The terse coaching segment Maya sees on a third sighting of import-order, and the JSONL bypass event when she ships a hot-fix:

——— 3c coaching ——— • import-order Why: imports should be ordered stdlib, third-party, local. ———————————————
{"ts":"2026-05-20T16:14:02Z","gate":"pre-commit","outcome":"bypass","reason":"prod hotfix #INC-417 — null-deref on /api/orders, fix in 3 lines","user":"maya","session":"hotfix-INC-417"}

What 3C does for you: coaching gets quieter, prompts get shorter, gates fire the same. Velocity compounds because the team's standards are doing the standardising, not the developers. What Maya still owns: the decision to bypass, the rationale she writes, the follow-up issue she files after shipping. What 3C does NOT do: erase the bypass — every event is permanent and reviewable.

Key takeaway
The framework gets out of your way as you internalise it. The first sighting is mentorship; the third is just a bullet.

07 · UAT
7 / 7

Walk the path. File the gap.

For #1287 (a UI change), Maya scaffolds an integration checklist via /3c-test --mode=integration, deploys to staging through /3c-deploy --env=staging, walks the checklist by hand, and uses /3c-bug to file the one regression she found — appended directly to the original issue with full environment capture.

The header of the /3c-bug report appended to issue #1287 (env values scrubbed):

Bug report — #1287 follow-up OS: macOS 14.5 (Darwin 23.5.0) Runtime: Node 20.12.2, npm 10.5.0 Project state: branch=feat/issue-1287..., commit=a8c4f2e Recent commits: 4 in last 24h Env (scrubbed): NODE_ENV=staging, FEATURE_FLAGS=[**SCRUBBED**] Repro: navigate /account, log out, log in as user with 0 orders Expected: empty-state copy. Actual: orders panel renders [object Object].

What 3C does for you: the integration checklist is generated, the environment is captured, the bug report is structured — no "works on my machine" archaeology. What Maya still owns: walking the checklist with human eyes; only humans notice that empty-state looks broken. What 3C does NOT do: deploy to production for her — production deploys require --yes on the deploy command.

Key takeaway
Manual UAT is the test the assistant cannot run. The framework's job is to capture what she found, structured.

Common mistakes · pinnable checklist

The assistant types.
You instruct.

Six wrong turns most teams make in their first week with 3C, and the one rule that summarises the rest. Print this page, pin it next to your laptop — the framework gets quieter as the team internalises it.

01 · Rubber-stamping AI issues
/3c-create-issue produces what you prompt, not what you mean. Read every issue body before publishing.
02 · Pasting the standards doc
Trust .claude/rules/ and the 150-instruction budget. Re-pasting blows the budget and degrades the model.
03 · Bypass without a real reason
The JSONL event is permanent and reviewable. "forgot why" in the reason field is how teams lose trust in the bypass mechanism.
04 · Treating coaching as noise
The second sighting goes terse on its own. Read it the first time and the framework gets quieter on its own.
05 · Implement on un-enriched issues
Enrich first (Phase 2), then implement. architect is cheaper before code than after.
06 · Hand-editing to "save time"
The assistant types, you instruct. Every hand-edit is a missed opportunity for the rule library to evolve.
